WeDirector

Long-horizon tool agents for end-to-end video editing.

WeDirector turns a plain narration script into a finished, multi-minute edited video. A single 9B policy model, trained with SFT then DAPO reinforcement learning, drives the whole thing: it segments the script, plans shots, synthesises narration, retrieves footage, chooses and fills animated templates, picks background music, reviews its own output, repairs what it does not like, and stitches the final cut — one tool call at a time, with no scripted pipeline telling it what to do next.

A typical run is around 12 tool calls over several minutes of video. There is no hand-written state machine: the trajectory is the model's.

How it works

code
narration script
  → POST /api/runs
  → one AICutRuntime per run (owns the authoritative editing state)
  → create_deep_agent(model=AICutChatModel, tools=12, system_prompt=training prompt,
                      middleware=[AICutGuardrailMiddleware])
  → LangGraph ReAct loop:
       AICutChatModel   rebuilds a single-turn state JSON from the authoritative
                        runtime state, calls the policy, parses one tool call
       Guardrail        preconditions / repetition / budget (rejects or halts;
                        never rewrites the model's decision)
       Tool             executes against the real environment
       Tool_StitchVideo succeeds → Command(goto=END)
  → events streamed to the browser over WebSocket
  → finished cut written to workspace/projects//

Two design choices are worth calling out, because they are what makes the agent behave the same in deployment as it did in training.

The runtime is the state authority. On every step the chat model discards the harness's accumulated message history and rebuilds a single-turn user message from the runtime's authoritative state. Tool schemas are regenerated from the same source of truth the training data generator used. What the model sees at inference is therefore byte-identical to what it saw during training — no drift from a growing conversation, no divergence between two schema definitions.

Guardrails observe, they do not correct. The middleware can reject a call whose preconditions are unmet, or stop a run that has exhausted its budget, but it never substitutes a different tool call. Illegal calls are fed back as observations and the model corrects itself. Every "helpful" server-side override is off by default (agent.autonomy.* in the config), because a policy that has been trained to recover is measured on whether it actually does.

The 12 tools

ToolWhat it does

Installation

Requirements

  • Python >= 3.11
  • For generation: an NVIDIA GPU with enough memory for a 9B model in bf16

(~24 GB). Frontend and API development need no GPU (--no-model).

  • Node >= 22 and ffmpeg, both installable via the setup script below.

1. Python dependencies

bash
git clone https://git.woa.com/chenyumu/WeDirector.git
cd WeDirector

pip install -r requirements.txt

# Inference only (GPU machines). Install torch matching your CUDA version first:
#   pip install torch --index-url https://download.pytorch.org/whl/cu121
pip install -r requirements-gpu.txt

ms-swift must be a build that registers the qwen3_5 model type. If yours does not, point model.ms_swift_path at a checkout that does, or export AICUT_MS_SWIFT_PATH.

2. External runtimes

bash
bash scripts/setup_external_tools.sh

This fetches ffmpeg, Node, the HyperFrames renderer, headless Chrome, GSAP and the subtitle font into external_tool/. Roughly 1.1 GB. Components already present are skipped, and each one has manual instructions in the matching external_tool/*/README.md if a download fails.

3. Model weights

bash
pip install -U "huggingface_hub[cli]"
hf download <org>/WeDirector-9B --local-dir checkpoints/wedirector-9b

Then either leave the default (checkpoints/wedirector-9b) or point at your own copy:

bash
export WEDIRECTOR_MODEL_PATH=/data/models/wedirector-9b

Full details, including sizes and how to skip individual components, are in docs/external_tools.md.

4. Check and run

bash
bash run_studio.sh --check     # validate every resolved path; no GPU needed
bash run_studio.sh             # start on the configured port
bash run_studio.sh --no-model  # UI + API only, no weights, no GPU

Open http://<host>:8081/. Weights load in the background over 30-60 seconds; the UI opens immediately and reports progress.

Plugging in your own footage and music

Retrieval is the one part of the system that has to be wired into whatever media you own, so it is a first-class extension point. Three options, in increasing order of effort.

Out of the box: open-web search

The default. Searches Bilibili / YouTube for footage and Internet Archive netlabels for CC-licensed instrumental BGM. No extra service, no API key for the Bilibili path.

yaml
services:
  retrieval_provider: asset_retrieval_tool

Config only: your own HTTP endpoint

If you already have a search service, describe it in YAML — no code:

yaml
services:
  retrieval_provider: http_video
  bgm_provider: http_bgm
  providers:
    http_video:
      url: https://footage.internal/search
      headers:
        Authorization: "Bearer ${FOOTAGE_TOKEN}"
      results_path: data.items
      field_map:
        clip_path: playback_url
        duration_sec: seconds

Response fields already named url, path, title or duration are matched automatically; field_map is only for the ones that are not.

A folder of files

yaml
services:
  retrieval_provider: local_folder_video
  bgm_provider: local_folder_bgm
  providers:
    local_folder_video:
      roots: [/data/my_footage]
    local_folder_bgm:
      roots: [/data/my_music]

Clips are matched on file name, parent directory names, and optional <name>.json sidecars carrying caption / tags / duration_sec.

Python: anything else

python
# my_providers.py
from pipeline.providers import VideoQuery, register_video_provider

@register_video_provider("my_footage")
def search(query: VideoQuery) -> list[dict]:
    hits = my_index.search(query.query, k=query.top_k)
    return [
        {"clip_path": h.path, "score": h.score,
         "duration_sec": h.seconds, "description": h.caption}
        for h in hits
    ]
yaml
services:
  retrieval_provider: my_footage
  providers:
    plugins: [my_providers]          # module name or /path/to/my_providers.py

Return whatever fields you have; the registry normalises them and fills in the rest. A provider that raises or returns nothing is treated as "no candidates" and the next backend runs, so a flaky source degrades instead of failing the run.

docs/providers.md has the full contract: the exact schemas, what each VideoQuery / BgmQuery field means, how the duration and orientation filters treat your results, and how to test a provider offline.

Using the studio

  1. Generate. Paste a narration script, press start. Eight live tracks

(segments, shots, narration, subtitles, footage, spotlight, BGM, render) fill in as the agent works, alongside its thinking, tool calls, and raw output. Pause, resume, or cancel at any point.

  1. Timeline. Multi-track view of every shot: position, duration, footage,

template. Click to select.

  1. Manual editing. On a selected shot: rewrite narration (re-runs TTS),

rewrite subtitles (does not), swap footage or template, delete, reorder, adjust BGM. Re-render touches only the shots you changed and re-stitches.

  1. Conversational editing. "Change the opening line to ...", "replace the

visual at 0:15". The model locates the target and proposes edits; destructive ones need confirmation.

  1. History. Past runs and finished projects, with version rollback.

Tests

Everything here runs offline, without a GPU:

bash
python3 tests/test_studio_offline.py           # config, tracks, editor, chat parsing, guardrails
python3 -m pytest tests/test_aicut_agent.py    # deepagents integration (mock loader + dispatch)
python3 -m pytest tests/test_retrieval_provider_switch.py   # provider routing
python3 -m pytest tests/test_providers.py      # provider registry and bundled providers
python3 -m pytest tests/test_thinking_parse.py # think/tool_call parsing
node tests/test_frontend.js                    # frontend (needs node)

test_aicut_agent.py asserts the properties that keep inference aligned with training: the model sees exactly the 12 trained tools (deepagents' built-ins are removed), format conversion round-trips, preconditions block correctly, a successful stitch terminates the graph, and plain-text conversation still works.

Notes for readers of the paper

AICutPipeline was this system's internal codename and still appears in the training system prompt and in the state JSON the model receives. Those strings are part of the training distribution and are deliberately left byte-identical — renaming them would move inference off-distribution. The public name is WeDirector.

configs/training/ holds the data-preparation and SFT configs behind the released checkpoint. They are not read at inference time.
