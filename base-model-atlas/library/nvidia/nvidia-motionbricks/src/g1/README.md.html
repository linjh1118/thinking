MotionBricks Unitree G1

Project page · Paper · Original G1 implementation

Model Description

MotionBricks Unitree G1 generates robot reference motion from recent motion, target poses, and root-motion constraints. Applications can update targets and feed generated motion back into the model to produce continuous locomotion and transitions. A separate controller is needed to execute that motion on a physical robot.

NVIDIA developed the original pretrained weights for the MotionBricks subproject in GR00T Whole-Body Control. This package stores those weights in SafeTensors format. The model uses a 34-joint skeletal representation of Unitree G1, with separate components for pose tokenization, pose prediction, and root-motion prediction. Its pose tokenizer is a vector-quantized variational autoencoder (VQ-VAE).

This model is intended for commercial and non-commercial motion-generation applications.

Where to Start

To run MotionBricks in an application, start with the G1 ONNX model and runtime. Use the checkpoints on this page to work with the individual PyTorch components or create ONNX exports. Download the complete G1 package, then follow the exporter guide. A training pipeline is not included.

Model Package

This card covers MotionBricks-G1-RP-v1 in the g1/ folder. The SOMA package is documented separately.

Model Architecture

Architecture Type: Modular latent generative model.

Network Architecture: Transformer-based pose and root predictors with a learned pose tokenizer and decoder. Recent motion, target poses, root constraints, and allowed duration condition generation. The pose predictor produces motion codes, which the decoder turns into skeletal-motion features. The root predictor generates root motion and duration.

Base Model: The original G1 components were trained from scratch on RP1 motion retargeted to G1. This release reuses those weights without retraining and packages them in SafeTensors format.

The model operates on the G1 skeletal representation. Application code converts between skeletal motion and the robot's joint angles.

The original G1 tokenizer uses eight heads with 10 codes per head and 32 dimensions per head. Use the matching G1 bundle and configuration for reproduction.

Number of Model Parameters: Approximately 195 million across the three components. The component counts below are rounded.

Inputs

Input Type(s): Skeletal-motion features, pose constraints, root-motion constraints, motion-token IDs, conditioning masks, and duration constraints. Text, images, audio, and video are not inputs to these checkpoint components.

Input Format(s): Numeric PyTorch tensors. Motion features use 32-bit floating point (FP32) with the bundled normalization statistics. Token IDs and lengths are integers. Constraint and padding masks are Boolean.

Input Parameters: The component tables below specify the tensor shapes and meanings.

Other Properties Related to Input: Context and target poses supply constraints on a short generation. The root predictor receives four context poses and four target poses. All components require their matching configuration and normalization statistics.

The three checkpoint components use the tensor interfaces below. N is the batch size, L is the number of motion-token positions, and T = 4L is the number of frames. Generation uses 6 to 16 tokens (24 to 64 frames) at 30 Hz. Shorter sequences can be padded and accompanied by their valid lengths. The checkpoint networks support batching. The practical batch size depends on memory and the inference implementation.

These are component-level interfaces after feature preparation. An application's pose interface or exported graph can differ.

For joint ordering, coordinate conventions, normalization, and motion reconstruction, use the matching MotionBricks implementation and the bundled configuration and skeleton metadata.

Outputs

Output Type(s): Motion codes and logits, reconstructed skeletal-motion features, root-motion predictions, and valid duration.

Output Format(s): Numeric PyTorch tensors. Motion features and root predictions use FP32. Motion codes and selected lengths are integers.

Output Parameters: The component tables above specify each output's shape and meaning. Output motion is represented at 30 Hz. Valid-length information distinguishes generated motion from padding.

Other Properties Related to Output: Longer motion requires repeated generation. Generated motion can supply the next context. The checkpoint-component interfaces differ from the joint coordinate interface of the combined ONNX export.

Together, the components generate root and body motion features. After denormalization and skeletal reconstruction, motion can be represented as root translations (N, T, 3) and joint rotation matrices (N, T, 34, 3, 3). The matching kinematic conversion can derive the robot's 29 joint angles.

Software Integration

Runtime Engine(s): PyTorch with the matching MotionBricks implementation, configuration, normalization statistics, and skeleton metadata. The exporter requires Python 3.12, PyTorch 2.14.0+cpu, NumPy 1.26.4, ONNX 1.23.2, and SafeTensors 0.8.0.

Supported Hardware Microarchitecture Compatibility: The exporter runs on the CPU. A specific CPU model, minimum-memory requirement, and broader compatibility matrix are not documented. For ONNX runtime requirements, see the G1 ONNX card.

Supported Operating System(s): We tested checkpoint-to-ONNX conversion on Windows. Tests on other operating systems are not reported.

The integration of foundation and fine-tuned models into AI systems requires additional testing using use-case-specific data to ensure safe and effective deployment. Following the V-model methodology, iterative testing and validation at both unit and system levels are essential to mitigate risks, meet technical and functional requirements, and ensure compliance with safety and ethical standards before deployment.

The exporter accepts the downloaded checkpoint folder. Its loader checks required file sizes and SHA-256 hashes, reads SafeTensors weights, and disables NumPy pickle loading. Keep the checkpoint and exporter versions matched. Do not load untrusted checkpoints. These checks do not replace security scans or validation in your application.

The original implementation provides model lineage and the earlier checkpoint-based demo. Its original PyTorch checkpoint loader is not directly compatible with this SafeTensors package.

The package omits optimizer, scheduler, callback, and training-loop state. It provides weights for inference or fine-tuning initialization with a compatible implementation, not exact resumption of the original training run.

Model Versions

MotionBricks-G1-RP-v1 contains the three original G1 components at training step 2,000,000. The manifest and checksums identify the package files. The accompanying software release is v0.2.0.

The components are used together. The MotionBricks exporter combines them into FP32 or mixed 16-bit floating-point (FP16) ONNX models. Those models have a separate card and a joint-coordinate interface. The export reuses the existing weights without retraining. It is not a newly trained joint-angle model.

Training, Testing and Evaluation Datasets

Training Dataset

Name/Identifier: Bones RigPlay 1 (RP1).

Data Modality: Other: human motion capture retargeted to the 34-joint Unitree G1 skeleton at 30 Hz. The model consumes motion features without text embeddings.

Training Data Size: 313,526 selected training clips. The approximately 700 hours describe the source corpus, not the selected training subset.

Data Collection Method: Automatic/Sensors. Bones captured human performances in a studio and supplied skeletal motion. NVIDIA used SOMA Retargeter to retarget that motion to G1, then converted it into model features. This preparation is not direct robot recording.

Labeling Method: Automatic/Sensors for captured skeletal motion, followed by automated retargeting and feature preparation. Text annotations are not model conditioning inputs in the supplied motion-only configuration.

Properties: G1 skeletal motion with a capture T-pose and dual-root representation, derived from a source corpus of approximately 350,000 RP1 clips and 700 hours of motion.

Linguistic Characteristics: Not applicable to the motion-feature inputs. Associated text descriptions are dataset metadata, not model conditioning inputs.

Testing Dataset

Name, Size and Role: We used 313,526 clips for training and a separate, selected set of 4,881 clips for validation and evaluation during training. No clips are shared between these sets. The 4,881 clips are a selection from the held-out pool, not the entire pool. A separate untouched final-test set, a performer-disjoint split, and the selected subset's duration are not documented.

Data Collection Method: Automatic/Sensors, from the same Bones studio motion-capture source as the training set. NVIDIA retargeted the human motion to the G1 representation.

Labeling Method: Automatic/Sensors for captured skeletal motion, followed by automated retargeting and feature preparation.

Properties: The validation inputs are 30 Hz skeletal-motion features on the 34-joint G1 representation. Text descriptions are selection metadata, not conditioning inputs. Linguistic characteristics are not applicable to these motion-only inputs. Disjoint clips alone do not rule out other forms of data leakage.

Evaluation Dataset and Results

Name/Size: Evaluation uses the same 4,881-clip RP1 subset described under Testing Dataset. It is not an additional independent test set.

Benchmark Score: A complete quantitative evaluation report for these checkpoint files is not included with this package.

Data Collection Method: Automatic/Sensors, using the same studio-captured human motion retargeted to G1.

Labeling Method: Automatic/Sensors for captured skeletal motion, followed by automated retargeting and feature preparation.

Properties: Evaluation uses the same 30 Hz G1 skeletal-motion representation as training. Text descriptions are selection metadata, not conditioning inputs. Linguistic characteristics are not applicable to the motion-only inputs. The subset's duration is unspecified.

Limitations

  • The model is specific to the bundled G1 kinematics and hinge order.
  • The generated poses do not enforce dynamic balance, actuator limits,

collision avoidance, or physical contact tracking.

  • Physical execution needs a downstream controller and application-specific

validation.

  • Generation uses a short sequence of context and target poses. Longer motion requires

repeated generation.

  • Numerical precision and backend differences can accumulate through feedback.
  • Scene geometry and text prompts are outside the model's conditioning interface.
