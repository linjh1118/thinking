MotionBricks SOMA

Project page · Paper

Model Description

MotionBricks SOMA generates human skeletal motion from recent motion, target poses, and root-motion constraints. Applications can feed generated motion back into the model and update targets to produce continuous locomotion and transitions between authored poses.

NVIDIA developed MotionBricks-SOMA-RP-v1 for the 30-joint SOMA skeleton using Bones RigPlay 1 (RP1) motion data. The checkpoint contains a pose tokenizer and decoder, a pose predictor, and a root predictor. Together, these components generate skeletal motion from the supplied constraints.

The package includes single-precision (FP32) weights in SafeTensors format, configuration, normalization statistics, and skeleton metadata. A training pipeline is not included.

This model is intended for commercial and non-commercial motion-generation applications.

Where to Start

To run MotionBricks in an application, start with the SOMA ONNX model and runtime. Use the checkpoints on this page to work with the individual PyTorch components or create ONNX exports. Download the complete SOMA package, then follow the exporter guide.

Intended Uses

MotionBricks SOMA is intended for developers and researchers building interactive human animation and motion previews for robotics and simulation. Applications can generate transitions between authored poses or update targets to guide locomotion. Generated motion is not validated for physical robot control.

Model Package

The SOMA model package contains SafeTensors weights, their supporting metadata, and this model card. Derived Open Neural Network Exchange (ONNX) exports and runtime software are maintained in the MotionBricks software repository.

The checkpoint package is organized under soma/ in the MotionBricks model repository. The three SOMA components are used together. The separate g1/ package is not covered by this card.

This card identifies the checkpoint as MotionBricks-SOMA-RP-v1. The accompanying software release is v0.2.0. The checkpoint name and software version describe different artifacts.

Download and Files

Download the complete soma/ folder and keep its directory structure intact. It contains separate directories for the pose vector-quantized variational autoencoder (VQ-VAE), pose predictor, and root predictor. No archive extraction is needed.

Each component includes checkpoints/model-step=1500000.safetensors, a JSON metadata sidecar, and supporting configuration files. Normalization arrays and skeleton metadata define the motion representation. Joint data is stored in joints.npy. Keep these files with the weights.

Use the manifest to identify package files and the checksums to verify their integrity.

The package omits optimizer, scheduler, callback, and training-loop state. It provides weights for inference or fine-tuning initialization with a compatible implementation, not exact resumption of the original training run.

Model Architecture

Architecture Type: Modular latent generative model.

Network Architecture: A pose vector-quantized variational autoencoder (VQ-VAE) encodes and decodes motion tokens. One transformer predicts motion tokens. Another predicts root motion and duration. The SOMA tokenizer uses five heads with 16 codes per head and 32 dimensions per head.

Base Model: The SOMA components were trained from scratch on RP1 motion. They are distinct from the original G1 model weights.

Number of Model Parameters: Approximately 200 million across the three components. The component counts below are rounded.

ComponentApproximate parameters
Pose VQ-VAE23.4 million
Pose predictor136.5 million
Root predictor40.4 million

Smart Primitives and locomotion controllers supply constraints at the application level. Text prompts are outside this model's conditioning interface. See the MotionBricks paper for the method. The paper reports experiments with the model configurations and datasets specified there.

Inputs

Input Type(s): Skeletal-motion features, pose constraints, root-motion constraints, motion-token IDs, conditioning masks and duration constraints. There are no text, image, video or scene-geometry inputs in these checkpoint interfaces.

Input Format(s): Numeric tensors consumed by the matching PyTorch implementation. Motion features are FP32 with bundled normalization statistics. Token IDs and lengths are integers. Dense constraint and padding masks are Boolean.

Input Parameters: Component-specific batched tensor shapes are listed below. N is batch size, L is the number of motion-token positions and T = 4L is the number of frames.

Other Properties Related to Input: Generation uses 6 to 16 tokens, corresponding to 24 to 64 frames at 30 Hz. Shorter sequences can be padded with valid-length masks. The root predictor uses eight boundary frames, four context frames and four target frames. Practical batch sizes depend on memory and implementation. These are checkpoint-component interfaces after feature preparation. An application's pose interface or exported graph can differ.

For joint ordering, coordinates, normalization and reconstruction, use the matching MotionBricks implementation and package metadata.

Each token represents four frames. The quantized latent has 160 values per token, five heads times 32 values. The table uses separate per-head code IDs. The implementation also supports packing them into one integer per token.

Outputs

Output Type(s): Motion codes and logits, reconstructed skeletal-motion features, root-motion predictions and valid duration. See the component tables above.

Output Format(s): Numeric tensors. Predicted motion features and root motion are FP32. Code IDs and selected lengths are integers. After denormalization and skeletal reconstruction, outputs can be represented as root translations (N, T, 3) and joint rotation matrices (N, T, 30, 3, 3).

Output Parameters: The component tables specify dimensions and valid lengths. Output motion is represented at 30 Hz. Respect valid-length information rather than treating padded frames as generated content.

Other Properties Related to Output: Longer motion requires repeated generation. Predictions may become context for a later call. Export precision and backend can change results. The checkpoint interfaces are not the same as the derived ONNX interfaces.

The model was trained using NVIDIA GPUs. The CPU-based export utility converts these checkpoints to ONNX. Its successful execution is not a real-time inference benchmark or a CPU-versus-GPU performance comparison.

Software Integration

Runtime Engine(s): PyTorch with the matching MotionBricks implementation, configuration, normalization statistics, and skeleton metadata. The exporter requires Python 3.12, PyTorch 2.14.0+cpu, NumPy 1.26.4, ONNX 1.23.2, and SafeTensors 0.8.0.

Supported Hardware Microarchitecture Compatibility: The exporter runs on the CPU. A specific CPU model, minimum-memory requirement, and broader compatibility matrix are not documented. For ONNX runtime requirements, see the SOMA ONNX card.

Supported Operating System(s): We tested checkpoint-to-ONNX conversion on Windows. Tests on other operating systems are not reported.

The integration of foundation and fine-tuned models into AI systems requires additional testing using use-case-specific data to ensure safe and effective deployment. Following the V-model methodology, iterative testing and validation at both unit and system levels are essential to mitigate risks, meet technical and functional requirements, and ensure compliance with safety and ethical standards before deployment.

The exporter accepts the downloaded checkpoint folder. Its loader checks required file sizes and SHA-256 hashes, reads SafeTensors weights, and disables NumPy pickle loading. Keep the checkpoint and exporter versions matched. Do not load untrusted checkpoints. These checks do not replace security scans or validation in your application.

Model Versions

MotionBricks-SOMA-RP-v1 contains the three FP32 components at training step 1,500,000. The manifest and checksums identify the package files.

The components are used together. The MotionBricks exporter combines them into FP32 or mixed FP16 ONNX models. Those models have a separate card and tensor interface. Use that interface when integrating the ONNX runtime. The checkpoint-component tensors are not interchangeable with the ONNX interface.

Training, Testing and Evaluation Datasets

Training Dataset

Name/Identifier: Bones RigPlay 1 (RP1).

Data Modality: Other: human skeletal motion capture, represented on the 30-joint SOMA skeleton at 30 Hz. Training used motion features without text embeddings.

Training Data Size: 313,526 human-motion clips in the selected training subset. The source corpus contains approximately 350,000 clips and 700 hours of motion. The source-corpus duration is not the selected training-subset duration.

Data Collection Method: Automatic/Sensors. Human performances were recorded in a motion-capture studio by Bones, then provided as skeletal motion. Training uses the processed uniform SOMA representation, not data captured directly on the SOMA skeleton.

Labeling Method: Automatic/Sensors for the captured skeletal motion, followed by automated preparation into uniform skeletal features. These motion-only runs use pose/motion values as their learning data and do not consume text embeddings or text annotations. The source dataset can include additional annotations, but those are not model conditioning inputs.

Properties: Training uses uniform SOMA motion features at 30 Hz, random first headings, and random crops of up to 15 seconds. Root motion and joint features provide the motion representation. Text embeddings and text augmentation are disabled. This package does not redistribute the training corpus.

Linguistic Characteristics: Not applicable to the motion-feature inputs. Associated text descriptions are dataset metadata, not model conditioning inputs.

All three checkpoint components were trained in FP32.

Testing Dataset

Name, Size and Role: We used 313,526 clips for training and a separate, selected set of 4,881 clips for validation and evaluation during training. No clips are shared between these sets. The 4,881 clips are a selection from the held-out pool, not the entire pool. A separate untouched final-test set, a performer-disjoint split, and the selected subset's duration are not documented.

Data Collection Method: Automatic/Sensors, from the same Bones studio motion-capture source and processed SOMA representation as the training set.

Labeling Method: Automatic/Sensors for captured skeletal motion, followed by automated preparation into the same motion features used for training. Text annotations are not consumed by the recorded motion-only validation path.

Properties: The validation inputs are 30 Hz skeletal-motion features in the same uniform SOMA representation as the training inputs. Linguistic characteristics are not applicable to these motion-only inputs. Disjoint clips alone do not rule out other forms of data leakage.

Evaluation Dataset and Results

Name/Size: Evaluation uses the same 4,881-clip RP1 subset described under Testing Dataset. It is not an additional independent test set.

Benchmark Score: A complete end-to-end benchmark of these SOMA checkpoints is not included with this package.

Data Collection Method: Automatic/Sensors. Same studio-captured Bones motion source, processed into the uniform SOMA representation.

Labeling Method: Automatic/Sensors for captured skeletal motion, with automated preparation into uniform motion features. Evaluation uses motion rather than text-conditioned labels.

Properties: Human skeletal motion represented on SOMA at 30 Hz. Linguistic characteristics are not applicable to these motion-only inputs. Text annotations are not consumed. The selected subset's duration is unspecified.

Recorded Results: The available evidence covers training-time observations and checkpoint conversion, not a complete final-checkpoint benchmark.

Inference

Acceleration Engine: The checkpoint implementation and exporter use PyTorch. The exporter runs on the CPU. The separate ONNX runtime uses TensorRT 10.8.

Test Hardware Set-Up: We tested checkpoint-to-ONNX conversion on Windows using CPU PyTorch. The CPU model, conversion time, and checkpoint-runtime latency and throughput are not reported. The ONNX card describes the separate Windows and RTX 4090 runtime. Neither successful export nor runtime execution establishes safe physical robot tracking.

Limitations

  • Output is specific to the SOMA joint layout and proportions.
  • Longer motion requires repeated generation from a short context window.
  • Targets guide motion, but the model does not receive scene geometry. Applications handle obstacles and target placement.
  • Generated motion can contain pose or contact artifacts and vary with numerical precision and inference backend.
  • Kinematic motion generation does not establish physical feasibility or successful tracking by a robot controller.
