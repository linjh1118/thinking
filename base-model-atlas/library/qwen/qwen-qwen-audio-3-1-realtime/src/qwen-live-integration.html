为语音助手和客服应用接入实时语音对话与工具调用。 
Qwen-Audio-Live 的前台模型负责听取用户语音、提问和回复。遇到需要调用业务接口或进行推理的任务，可以把任务交给应用或后台模型，继续与用户对话。 
以查订单为例，查询期间，前台模型仍可以接收用户补充的订单号，并播报查询进展和结果。Client 模式由应用处理任务并回传结果。Responses 模式由百炼调用配置的后台模型处理任务，并将结果交给前台模型。 
会话配置、音频收发和用量查询见 管理会话 。接入业务系统或后台模型见 任务委派与工具 。 
快速开始 
想先验证接入，可以 运行本页的 Python 示例 ，发送一段录音，检查能否收到字幕和音频。 
想直接和模型对话，可以 运行 WebRTC 浏览器示例 ，用麦克风说话，并听取模型回复。 
建立第一个会话 
本例通过 WebSocket 将一段录音发送给模型，并将语音回复保存到 reply.wav 。 准备录音和凭证 
准备华北 2（北京）的业务空间 ID 和 API Key 。长期 API Key 保存在应用服务端。 
安装 Python 和 FFmpeg。录一句「请从一数到三」，保存为 input.wav 。 
将 API Key 配置到环境变量 DASHSCOPE_API_KEY ，然后安装依赖，并将录音转换为 16 kHz、16 位、单声道的 PCM 音频。 python -m pip install "websockets>=15"
ffmpeg -i input.wav -ar 16000 -ac 1 -f s16le input.pcm 发送录音并接收回复 
Qwen-Audio-Live 仅支持业务空间专属域名。这个示例连接华北 2（北京），请在代码中填写该地域的业务空间 ID。 
示例中的两个模型参数已经填好。连接地址里的 model 用于接入 Qwen-Audio-Live 服务， session.model 则指定与用户交谈的前台模型。本例使用 qwen-audio-4.0-realtime-preview ，并将 turn_detection.type 设为 duplex ，开启全双工对话。此时模型可以边听边说，在回复时仍能接收用户语音。其他会话设置见 session.update 。 
将以下示例保存为 live_quickstart.py 。 import base64
import json
import os
import sys
import time
import uuid
import wave
from pathlib import Path

from websockets.sync.client import connect

WEBSOCKET_URL = "wss://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/realtime?model=qwen-audio-3.1-live"
SESSION_MODEL = "qwen-audio-4.0-realtime-preview"
REPLY_TIMEOUT_SECONDS = 12


def main():
    audio = Path(sys.argv[1]).read_bytes()
    if not audio or len(audio) % 2:
        raise ValueError("请提供非空的 16 位 PCM 文件")
    headers = {"Authorization": f"Bearer {os.environ['DASHSCOPE_API_KEY']}"}
    with connect(
        WEBSOCKET_URL,
        additional_headers=headers,
        close_timeout=2,
    ) as ws:
        def send(event_type, **payload):
            ws.send(json.dumps({
                "type": event_type,
                "event_id": uuid.uuid4().hex,
                **payload,
            }))

        session = {
            "model": SESSION_MODEL,
            "modalities": ["text", "audio"],
            "turn_detection": {"type": "duplex"},
            "delegation": {"type": "client"},
        }
        send("session.update", session=session)

        deadline = time.monotonic() + 20
        while True:
            event = json.loads(ws.recv(timeout=max(0, deadline - time.monotonic())))
            if event["type"] == "session.updated":
                break
            if event["type"] in ("error", "session.closed"):
                raise RuntimeError(event)

        audio += bytes(32000 * 3)
        with wave.open("reply.wav", "wb") as reply:
            reply.setparams((1, 2, 24000, 0, "NONE", "not compressed"))
            start = time.monotonic()
            offset = 0
            deadline = start + len(audio) / 32000 + REPLY_TIMEOUT_SECONDS
            while time.monotonic() < deadline:
                if offset < len(audio) and time.monotonic() >= start + offset / 32000:
                    frame = audio[offset:offset + 640]
                    send("session.input_audio.append",
                         audio=base64.b64encode(frame).decode("ascii"))
                    offset += len(frame)
                try:
                    event = json.loads(ws.recv(timeout=0.02 if offset < len(audio) else 0.25))
                except TimeoutError:
                    continue
                event_type = event["type"]
                if event_type == "session.output_audio.delta":
                    reply.writeframesraw(base64.b64decode(event["delta"]))
                elif event_type == "session.output_transcript.delta":
                    print(event["delta"], end="", flush=True)
                elif event_type == "session.closed":
                    break
                elif event_type == "error":
                    raise RuntimeError(event["error"])
            else:
                send("session.close")
                close_deadline = time.monotonic() + 2
                while time.monotonic() < close_deadline:
                    try:
                        event = json.loads(ws.recv(timeout=max(0, close_deadline - time.monotonic())))
                    except TimeoutError:
                        break
                    if event["type"] == "session.closed":
                        break
            if not reply.getnframes():
                raise RuntimeError("未收到语音回复")

选择接入方式 
两种接入方式都先建立 WebSocket 主连接。您可以用这条连接直接收发音频，也可以另外建立一条 WebRTC 或 AOQ 媒体连接来收发音频。 

仅用 WebSocket 。适合用录音验证接入，或由服务端直接处理音频。音频、字幕和任务事件都走同一条连接。 

WebSocket + WebRTC 或 AOQ 。保留 WebSocket 主连接，用它配置会话、协商媒体连接和发送任务请求。媒体连接就绪后，用它收发音频，同时可从 WebSocket 主连接或媒体连接接收服务端事件。 
WebRTC 。适合在浏览器或应用中实时采集和播放语音。通过控制 WebSocket 交换 SDP。 
AOQ 。适合已集成 AOQ Client SDK 的应用。通过控制 WebSocket 获取临时凭证，再用 SDK 连接 Relay。 
API 参考 按操作提供请求与响应事件的入口。 模型详情 列出地域、限流和价格。 
编写提示词 
编写前台对话提示词 
在 session.instructions 中设置前台的角色和语气，说明何时追问、何时委派，以及如何播报结果。 
初次配置会话时，省略 session.instructions 会使用内置提示词。如果填写了自定义提示词，它会替换内置提示词，因此请把对话需要遵循的规则写完整。 
要让客服先简短回答，再问客户是否需要帮助，可在 session.update 的 session 中加入以下字段，并保留已有的 model 和 delegation 等设置。 {
  "instructions": "担任门店客服。先用一句话回答，再询问用户是否需要其他帮助。"
} 
编写任务处理规则 
任务提示词说明处理步骤、输入校验和结果格式。用 Client 模式时，在应用或 Agent 中定义这些规则。用 Responses 模式时，在 session.delegation.responses.instructions 中写明后台模型需要遵循的规则，百炼没有内置的后台提示词。 
用提示词分配计算任务 
在 Responses 模式下，可以让前台问清计算条件，由后台计算总价。 
前台提示词 说明何时追问、何时交给后台。例如，缺少单价或数量时，先向用户确认。条件齐全后，把计算任务交给后台模型，并在收到结果后用一句话播报。 
后台提示词 说明怎么算、返回什么。例如，根据单价和数量计算总价，返回金额和币种。 
完整的会话配置和验证步骤见 Responses 模式示例 。 
管理会话 
建立连接后，先配置会话，确定由哪个前台模型和用户交谈、使用什么音色、如何传输音频，以及任务交给谁处理。 
配置会话 
设置 配置位置和用途 
前台模型 通过 session.model 选择与用户交谈的模型。要开启全双工对话，选择 qwen-audio-4.0-realtime-preview ，并将 session.turn_detection.type 设为 duplex 。 
对话指令和音色 通过 instructions 和 voice 设置。见 编写提示词 和 配置音色 。 
输出类型 modalities 同时包含 text 和 audio 时，服务返回语音和字幕。 
音频传输方式 通过 session.transport 选择音频走哪条连接。省略时，音频通过 WebSocket 收发。使用 WebRTC 或 AOQ 时，按各自的 接入流程 建立媒体连接。 
任务处理模式 通过 session.delegation 设置。见 任务委派与工具 。 
发送 session.update 后，通过 session.updated 确认哪些配置已生效。仅用 WebSocket 时，收到该事件后就可以发送音频。使用 WebRTC 或 AOQ 时，还要等媒体连接就绪。 
配置音色 
在 session.update 的 session 对象中设置音色 ID，保留其余会话配置。 {
  "voice": "qingyou"
} 
示例中的 qingyou 对应「青柚」，默认值为 yunshu （云舒）。完整列表见 客户端事件 。 
收发语音和字幕 
发送麦克风音频和播放模型回复时，使用建连时选定的音频通道。开启全双工对话后，播放回复时也要继续采集并发送用户语音，同时读取服务端事件。 
WebRTC 通过媒体轨道收发音频。浏览器收到远端音轨后，将它交给播放器。 
AOQ 通过 SDK 发送用户语音和播放模型回复。上行音频必须通过 AOQ 发送。将 session.transport.aoq.ws_audio 设为 true 后，控制 WebSocket 也会收到一份模型的回复音频。详见 AOQ 接入 。 
WebSocket 通过 JSON 事件收发音频。输入和输出都使用单声道 PCM，采样率见下表。 
下表的音频收发流程适用于纯 WebSocket 接入。字幕事件适用于三种接入方式。 
数据 事件 处理方式 
麦克风音频或录音 发送 session.input_audio.append 将 16 kHz、16 位、单声道 PCM 音频分片并编码为 Base64。快速开始以 20 毫秒为一帧。 
模型回复音频 接收 session.output_audio.delta 解码事件的 delta ，按到达顺序播放 24 kHz、16 位、单声道 PCM。 
字幕 接收 session.input_transcript.delta 和 session.output_transcript.delta 前者是用户语音的转写，后者是模型回复的字幕。 
如果用户在模型播报时补充一句话，用户字幕和模型字幕可能同时更新。将两路字幕分别追加到各自的对话气泡，并根据播放器的实际状态更新界面上的播报指示。 
WebRTC 或 AOQ 媒体连接就绪后，控制 WebSocket 和媒体连接都可用于接收字幕。如果两路都收到同一个 event_id ，只追加一次。 
如果界面有麦克风开关，可在用户切换时发送 session.input_audio.mute 或 session.input_audio.unmute ，等服务确认后再更新开关状态。静音期间，会话仍保持连接。 
发送文字消息 
除了语音，用户也可以在通话中用文字补充信息，例如输入要查的商品名。应用通过 session.item.create 将这段文字作为用户消息发给模型。 {
  "type": "session.item.create",
  "event_id": "evt_user_message",
  "item": {
    "role": "user",
    "type": "message",
    "content": [
      {"type": "input_text", "text": "我想查黑色折叠伞。"}
    ]
  }
} 
结束会话和查看用量 
单次会话没有时长上限，费用按会话时长（秒）计算。连接建立后至少计费 3 秒，超过 3 秒则按实际会话时长计费。发送文字消息、静音和空闲的时间都计入会话时长。百炼调用后台模型时，还会按该模型的实际 Token 用量另行计费。 
用户挂断或点击结束时，发送 session.close 并停止采集麦克风音频。等收到 session.closed 后，再关闭连接并释放资源。 
会话激活后，服务每 5 秒通过 session.usage.updated 上报 usage.seconds ，表示会话累计计费时长（秒）。会话期间取最新值，结束后以 session.closed 中的 usage.seconds 为准。价格及后台模型计费见 计费说明 。 
排查接入问题 
问题现象 排查方法 
上传音频后没有回复 先确认收到 session.updated 。纯 WebSocket 接入时，检查上行音频是否为 16 kHz、16 位、单声道 PCM。使用 WebRTC 或 AOQ 时，确认媒体连接已就绪，并已通过该连接发送音频。 
收到字幕，未听到语音回复 纯 WebSocket 接入时，检查是否收到 session.output_audio.delta ，并以 24 kHz 播放。使用 WebRTC 或 AOQ 时，检查播放器是否接收到所选通道的下行音频。 
任务已处理，未听到语音播报 检查应用是否接收并播放前台模型的语音。Client 模式下，确认回传的 delegation_id 与任务一致。 
收到 error 或 session.closed 收到 error 时，按 错误事件 检查请求。会话关闭后，如需继续通话，重新建连并配置会话。 
任务委派与工具 
本节示例沿用 快速开始 的纯 WebSocket 连接。使用 WebRTC 或 AOQ 时，会话配置和任务请求仍通过控制 WebSocket 发送，音频则通过媒体连接收发。 
前后台工具选型 
用户在对话中提出业务请求时，前台模型可以直接发起函数调用，也可以把任务委派给后台。接入时，可以根据任务的处理步骤和响应要求，选择把工具配置在哪里。 
前台工具 适合可直接执行、需要快速响应的操作。例如，用户说「播放音乐」时，前台模型调用通过 session.tools 注册的函数，由应用执行播放指令。 
后台工具 适合需要判断条件或依次调用多个工具的任务。例如，办理改签时，后台先查询订单和改签规则，再查找可选班次。前台模型收到结果后，向用户说明有哪些班次可选。 
选择处理任务模式 
希望百炼调用后台模型并传回结果时，选择 Responses 模式 。已有业务接口、工作流或 Agent，或者需要由应用先核对结果再决定播报内容时，选择 Client 模式 。 
在 session.update 中设置 session.delegation.type 。Responses 模式填 responses ，Client 模式填 client 。 
要决定的事 Responses 模式 Client 模式 
谁处理任务 百炼调用配置的后台 Responses 模型。 应用调用业务接口、工作流、Agent 或模型。 
谁准备任务输入 百炼根据会话发起后台请求，应用配置后台模型和任务指令。 应用从委派事件读取任务摘要和上下文，结合业务数据构造请求。 
谁决定回传什么 后台结果由百炼交给前台模型。 应用可以校验、汇总或筛选结果，再把适合播报的内容交给前台模型。 
例如，只需根据用户给出的单价和数量计算总价，可以用 Responses 模式。查询库存需要按门店权限调用内部接口，并由应用校验结果，可以用 Client 模式。 
两种模式都可以 配置前台函数 ，用 call_id 将函数调用与结果对应起来。Client 模式中的任务委派则使用 delegation_id 关联同一任务的进度、追问和结果。接入业务系统前，先确认应用拥有接口权限，并了解接口需要哪些输入、会返回什么。
