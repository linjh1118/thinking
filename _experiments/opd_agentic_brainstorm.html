现有工作的空白地图

为什么 Agentic OPD 是重要方向？

LLM OPD 的 rollout 是一条 token 序列，损失可以逐 token 独立计算。Agent OPD 的 rollout 是一条多步决策链，每步动作会改变环境状态、影响后续观察——这使得信用分配（credit assignment）、教师信号对齐、分布漂移校正都变得非常困难。现有 5 篇 Agentic OPD 论文（SCoRe、OpenClaw-RL、RPD、VLA-OPD、LLM4Teach）几乎都是"把 OPD 搬到 Agent"的工程工作，缺乏系统理论和专为 Agent 设计的算法创新。

① 关键步骤识别
轨迹中哪些步骤值得 OPD？均匀施加是巨大浪费，无人系统研究。
② 无外部教师的 Agentic OPSD
LLM 有 OPSD，Agent 场景几乎没有同等的"自我蒸馏"方案。
③ 轨迹级 KL vs 序列 RL
KL 信号在多步轨迹上如何传播？与 RL 优势的交互尚无理论。
④ 异步 / 延迟 OPD
Agent 执行耗时长，教师与学生无法同步；离线+在线混合方案空白。
⑤ 多 Agent 协同蒸馏
多个学生 Agent 协作，教师如何跨 Agent 提供一致信号？
⑥ 安全约束下的 OPD
真实部署需要保证 Agent 不做危险动作，OPD 和安全约束如何共存？
⑦ 工具调用幻觉专项
工具调用错误（参数幻觉、函数名错误）与自然语言错误结构不同，无专项方案。
⑧ 长程规划 OPD
50+ 步任务的教师信号如何有效传播？折扣因子 vs 稀疏锚点争议未解。

01

CausalOPD：因果关键步识别 + 稀疏 OPD 信号

"不是所有步骤都值得 OPD——只需要纠正轨迹分叉点"
新颖度 ★★★★★ 可行性 ★★★★ 影响力 ★★★★★
新颖度
可行性
影响力
核心问题

Agent 轨迹中均匀施加 OPD 是低效的——工具调用参数格式错误（步骤 3）和最终错误答案（步骤 20）应该获得截然不同的 OPD 权重。但如何自动识别"因果关键步"？

核心方法

用反事实因果分析定义步骤重要性：

Importance(k) = E[R(τ)] - E[R(τ | do(a_k ← a_k*))]

即"如果第 k 步换成教师动作，轨迹结果会改善多少"。Importance 大 → 这是关键步，施加高权重 OPD。

实现路径
  • 用蒙特卡洛近似：重新执行轨迹（替换步骤 k），估计结果变化
  • 或用轻量代理模型估计 Importance（离线预计算）
  • OPD 损失改为加权版：L = Σ_k Importance(k) · KL(π_T(·|o_k) ‖ π_S(·|o_k))
基线对比
  • vs 均匀 OPD（SCoRe 风格）
  • vs 只纠正最后错误步（SCoRe 原论文）
  • vs GRPO 纯 RL
发表定位 & 差异化

目标会议：NeurIPS 2026 / ICML 2026 / ACL 2026
差异化：SCoRe 只纠正"最早错误步"，这是启发式的；CausalOPD 是数学上可定义的最优稀疏权重方案，具备理论保证（在 tabular MDP 下可以证明 Importance 权重最小化期望 KL 代价）。
故事线："Agent 任务中 OPD 应该是稀疏的，而不是稠密的——我们证明了哪里应该稀疏，哪里应该稠密。"

02

AOPSD：Agentic On-Policy Self-Distillation（无外部教师）

"同一个 Agent，在'后知之明状态'和'当前状态'之间蒸馏自己"
新颖度 ★★★★★ 可行性 ★★★★★ 影响力 ★★★★★
新颖度
可行性
影响力
核心洞察

OPSD 在 LLM 推理中用"已知答案"作为特权上下文（教师），在 Agent 场景中，"已知完整轨迹结果"就是天然的特权上下文。一个执行完成任务的 Agent，在知道后续所有状态后，可以重新评估每一步应该怎么做——这就是 Agent 版的自蒸馏。

核心方法：回溯条件自蒸馏

教师端（同一模型 + 后知之明上下文）：

输入：(o_k, a_{k..T}, o_{k+1..T}, R_total)  （知道后续轨迹和结果） π_T(a_k | o_k, future_context)

学生端（同一模型，只有当前观察）：

y_k ~ π_S(a_k | o_k, history)  （on-policy） L = Σ_{k∈success_steps} RKL(π_S ‖ π_T_hindsight)
无需外部教师的实现
  • 成功轨迹（R=1）全部作为自蒸馏数据源
  • 后知之明 prompt 格式："你刚刚完成了任务，回顾步骤 k，请给出当时最优的动作选择"
  • 教师 logit 来自同一模型的两次 forward（前向带 future_context，反向不带）
  • 计算成本：只需存储成功轨迹，额外 1× forward pass
与 OpenClaw-RL 的区别

OpenClaw-RL 用另一个判别模型提取后知之明 prompt，本方案用同一个模型 + 简单模板实现自蒸馏，完全无需外部模型，成本降低 50%+，可扩展到任意 Agent 场景。

发表定位 & 故事线

目标会议：ACL 2026 / EMNLP 2026 / NeurIPS 2026
故事线："OPSD 让 LLM 用'已知答案'教自己；我们把同样的思想带到 Agent——Agent 用'完成后回望'教自己当时该怎么做。无需 72B 外部教师，7B Agent 用自己的成功经验训练自己，在 12 个 benchmark 上达到接近 72B 教师的效果。"
关键实验：与 SCoRe（72B 教师）对比，证明 AOPSD（无外部教师）差距在 2pp 以内。

03

ToolOPD：工具调用幻觉的专项在策略蒸馏

"工具调用错误有结构——函数名 / 参数名 / 参数值各需要不同的 OPD 策略"
新颖度 ★★★★ 可行性 ★★★★★ 影响力 ★★★★
新颖度
可行性
影响力
问题背景

工具调用（Function Calling）错误有三层结构：(1) 函数名幻觉（调用不存在的函数）；(2) 参数名错误（正确函数但参数名写错）；(3) 参数值错误（参数名对但值类型错/超出范围）。现有 OPD 把工具调用 token 与普通 token 一视同仁，失去了结构信息。

结构化 Token 重加权

将工具调用 JSON 按语法层级分组：

w_func > w_param_name > w_param_value > w_reasoning

函数名 token 获得最高 OPD 权重（错了整个调用就失败），参数值 token 权重最低（部分容错）：

L = Σ_t w(token_type_t) · KL(π_T ‖ π_S) at token t
工具感知验证器
  • 执行每条 rollout 中的工具调用，收集执行结果（成功/报错/返回值）
  • 报错类型 → 自动推断错误层级（名称不存在 → 函数名错误；类型错误 → 参数值错误）
  • 根据错误层级动态调整 w(token_type)：错误层级越高，对应 token 组权重越大
为什么现有方案不够？

ToolBench/APIBench 的标准方法是 SFT-on-correct-calls。OPD 方案（SCoRe）只关注"最早错误步"，没有区分错误在工具调用 JSON 中的位置。ToolOPD 直接在 token 类型层面操作，粒度更细。

发表定位

目标：ACL 2026 / NAACL 2026
故事线："工具调用不是普通 token 序列——它有语法结构。我们设计了第一个工具感知的 OPD 框架，在 ToolBench/APIBench/ToolACE 上超过基线 10%+，且只需要工具执行结果（无需人工标注）。"
数据：可以直接用公开的 ToolBench、ToolACE、API-Bank 数据集，验证器用工具执行器自动生成。

04

AsyncOPD：异步在策略蒸馏（Agent 执行与 OPD 训练解耦）

"Agent 任务耗时分钟级，OPD 训练不能等每步执行结束——需要异步解耦"
新颖度 ★★★★ 可行性 ★★★ 影响力 ★★★★
新颖度
可行性
影响力
问题

SWE-bench / WebArena 等真实 Agent 任务每条轨迹耗时 5-30 分钟。如果等轨迹完成再做 OPD，GPU 利用率极低（执行时 GPU 空闲）。反之若并行执行 + 实时 OPD，需要解决学生策略在执行过程中已经更新带来的 off-policy 问题。

AsyncOPD 架构
  • 执行池：N 个并行 Agent 实例在环境中执行任务（收集轨迹片段）
  • 缓冲区：滚动窗口（最近 K 条已完成步骤 + 教师 logit 预计算）
  • 训练池：从缓冲区采样，用重要性采样修正 off-policy 偏差
    • w_IS(a_k) = π_S_current(a_k|o_k) / π_S_old(a_k|o_k)
  • 当 w_IS 超出 [0.5, 2.0] 范围时，丢弃该样本（防止严重 off-policy）
关键技术挑战
  • 教师 logit 预计算：执行完步骤 k 后立即异步调用教师计算 logit，不阻塞执行
  • 分布 drift 检测：监控 w_IS 分布，drift 严重时暂停训练等轨迹刷新
  • 轨迹级 vs 步骤级采样：优先采样高质量成功轨迹的早期步骤
工程价值

AsyncOPD 可以将 GPU 利用率从 30%（等待执行）提升到 85%+，使 Agent OPD 的实际训练吞吐量提升 2-3×。对于长周期任务（SWE-bench）这是实际可用性的关键。

发表定位

目标：ICML 2026 Systems Track / NeurIPS 2026
故事线："Agent 任务的时间特性与 LLM 生成根本不同——我们设计了第一个异步在策略蒸馏框架，让 GPU 利用率从 30% 到 85%，同时用重要性采样保证训练质量，在 SWE-bench 和 WebArena 上同等效果下训练速度快 2.8×。"

MultiAgentOPD：多 Agent 协同场景的分布式在策略蒸馏

"当多个 Agent 合作完成任务，教师信号如何跨 Agent 保持一致？"
新颖度 ★★★★★ 可行性 ★★★ 影响力 ★★★★
新颖度
可行性
影响力
问题背景

现实 Agent 系统往往是多 Agent 的：一个 Orchestrator + 多个 Executor（如 SWE-agent、AutoGen 风格）。单个 Agent 的 OPD 研究无法处理跨 Agent 信用分配——Executor A 的工具调用错误导致 Orchestrator 的规划失败，两者都应该学，但如何协同蒸馏？

核心方法：角色分离 OPD
  • Orchestrator OPD：用任务级结果 R_global 作为 RL 信号 + 教师 Orchestrator logit 做 KL
  • Executor OPD：用子任务完成率 R_sub + 教师 Executor logit 做 KL
  • 跨 Agent 一致性约束：
    • L_consist = KL(π_orchestrator(subtask|state) ‖ π_executor_capability(subtask))

    确保 Orchestrator 分配的任务在 Executor 的能力范围内

两种教师配置
  • 同构教师：同一个大模型扮演 Orchestrator 和 Executor 教师（无需两个模型）
  • 异构教师：专门的 Orchestrator 大模型（GPT-5 Turbo）+ 专门的 Executor 大模型（代码模型）

实验对比两种配置的效果和成本权衡。

Benchmark 选择
  • SWE-bench Multi-agent（Orchestrator + Coder + Tester）
  • GAIA Level 3（需要多步信息检索协作）
  • 自建：OpenClaw Multi-agent 场景
发表定位

目标：NeurIPS 2026 / ICLR 2027
故事线："OPD 至今只研究单个 Agent。我们首次定义多 Agent OPD 问题，提出角色分离 + 跨 Agent 一致性约束，在 SWE-bench Multi-agent 和 GAIA L3 上实现 SOTA，并证明同构教师方案只需单一大模型即可达到异构教师 95% 的效果。"

SafeOPD：安全约束下的 Agentic 在策略蒸馏

"教师告诉学生该怎么做，但某些动作是绝对禁止的——如何同时满足？"
新颖度 ★★★★ 可行性 ★★★★ 影响力 ★★★★★
新颖度
可行性
影响力
核心张力

真实 Agent 部署有硬安全约束：不能删除生产数据库、不能发送未审核的邮件、不能执行危险 shell 命令。OPD 让学生逼近教师分布，但如果教师的某些动作违反安全约束怎么办？强行 KL 蒸馏会把危险动作也学进来。

SafeOPD：约束 CMDP + 安全掩码

将安全约束建模为 CMDP（约束 MDP），OPD 目标改为：

max_{π_S} E[R] - β·KL(π_S ‖ π_T) s.t. E[C(a)] ≤ δ  （安全代价约束）

安全掩码机制：在动作空间上施加二值掩码 M(a)，对违反安全约束的动作：

L_safe = L_OPD + λ · max(0, E[M(a)·π_S(a|o)] - δ)
安全约束的三个来源
  • 规则基础：正则表达式匹配危险命令（rm -rf / DROP TABLE 等）
  • 语义基础：小型安全分类器判断动作意图
  • 人工红线：用户定义的禁止动作列表（JSON 格式）
Benchmark 与应用场景
  • SafeAgentBench（已有数据集）
  • AgentHarm（恶意指令下的安全率）
  • 企业 IT 自动化（运维 Agent，shell 操作安全）
发表定位

目标：ACL 2026 / NeurIPS 2026（Safety Track）
故事线："OPD 让 Agent 快速提升能力，但能力提升不等于安全提升——事实上，无约束 OPD 可能把教师的危险行为也蒸馏进学生。SafeOPD 是第一个将安全约束系统性整合进 Agentic OPD 的框架，在能力损失 <2pp 的前提下将危险动作率降低 90%+。"
战略价值：AI 安全是顶会必收热点，SafeOPD 卡住了"Agent OPD + 安全"这个交叉口。

07

TrajectoryCompressOPD：长程 Agent 轨迹的压缩蒸馏

"50 步轨迹 → 20 步但效果相同——Agent 的 CRISP"
新颖度 ★★★★ 可行性 ★★★★ 影响力 ★★★★
新颖度
可行性
影响力
问题：Agent 轨迹的冗余

Agent 在完成任务时往往有大量冗余步骤：重复确认、多余的探索性工具调用、不必要的中间检查。CRISP 用"请简洁"指令压缩 LLM 推理链，Agent 场景有类比：用"尽量用更少步骤"指令压缩 Agent 轨迹，用 OPD 让学生在没有指令时也能自动简洁执行。

方法：步骤级 CRISP 类比
教师 = 同模型 + "请用最少步骤完成任务" 系统 prompt 学生 = 同模型，正常推理（可能多步）

OPD 损失：在学生 rollout 的每个决策步骤上计算与压缩教师的 KL：

L = Σ_k RKL(π_S(a_k|o_k,hist) ‖ π_T_concise(a_k|o_k,hist,"简洁"))

同时保留成功率约束：任务完成率 ≥ 基线 - 3%

技术挑战
  • 轨迹步数不同的对齐问题（压缩轨迹 15 步 vs 原轨迹 40 步如何对齐 KL？）
  • 解决方案：用 DTW（动态时间规整）在步骤序列上对齐，再施加 KL
  • 或：在关键决策步（工具调用步）上对齐，跳过中间推理步
实验设计
  • Benchmark：WebArena（默认约 20 步/任务）、SWE-bench（约 40 步）
  • 指标：平均步数↓ vs 任务成功率（Pareto 前沿）
  • 对比：RL + 步数惩罚 vs TrajectoryCompressOPD
发表定位

目标：EMNLP 2026 / COLM 2026
故事线："真实 Agent 部署的推理成本随步数线性增长。我们将 CRISP 的轨迹压缩思想带到 Agent，用自蒸馏让 Agent 学会'高效执行'——步数减少 40%，成功率损失 <2%。CRISP 没有做 Agent 版本，我们来做。"
实用价值：40% 步数减少 = 40% API 调用减少 = 40% 推理成本节省，对企业用户直接可见。

08

RetroOPD：回溯优化的在策略蒸馏（失败轨迹的价值最大化）

"失败轨迹不是废数据——从失败中提取密集 OPD 信号"
新颖度 ★★★★ 可行性 ★★★★★ 影响力 ★★★★
新颖度
可行性
影响力
观察

Agent 早期训练的失败率高达 60-80%。现有方法（SCoRe、AOPSD）主要利用成功轨迹做自蒸馏，失败轨迹要么丢弃（GRPO 负样本），要么只用于找"第一个错误步"。失败轨迹其实包含大量"在哪里分叉"的信息，这是最有价值的学习信号。

RetroOPD：失败轨迹回溯修复

Step 1：对失败轨迹，找到"分叉点" k*（如果从 k* 开始改变，任务可能成功）

k* = argmax_k P(success | do(a_k ← a_k_teacher))

Step 2：从 k* 开始用教师重新执行（Intervention rollout），生成成功版本

Step 3：在 k* 之前的步骤，施加低权重 OPD（这些步骤是对的）

Step 4：在 k* 处，施加高权重 OPD（这是最关键的纠正点）

L = w_correct · L_OPD(前 k* 步) + w_critical · L_OPD(第 k* 步) w_critical ≫ w_correct
分叉点检测方法
  • 二分搜索：对轨迹中点做 Intervention，判断成功率变化，迭代缩小分叉点范围
  • 代理模型估计：训练轻量级分类器预测"从步骤 k 继续有多大可能成功"
  • 规则启发式：第一个返回 error/exception 的工具调用步 ≈ 分叉点（适合工具调用场景）
与 SCoRe 的区别

SCoRe 纠正"最早的错误步"（局部启发式）；RetroOPD 纠正"对结果影响最大的步骤"（全局因果视角）。在实验中，两者差异在复杂任务（WebArena Level 3）上约 5-8pp，在简单任务上差异不大。

发表定位

目标：NeurIPS 2026 / ICML 2026
故事线："Agent 训练中 60-80% 的轨迹是失败的，现有方法只利用成功轨迹做 OPD——等于浪费了大多数数据。RetroOPD 从失败轨迹中提取密集 OPD 信号：通过因果干预找到分叉点，在最关键的纠正步施加高权重蒸馏，数据利用率提升 3×，在 WebArena 和 SWE-bench 上超过 SCoRe 8%+。"
